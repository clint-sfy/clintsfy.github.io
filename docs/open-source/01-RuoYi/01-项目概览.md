# 项目概览

## 本篇目标

先回答三个问题：这个仓库解决什么问题、可运行应用从哪里启动、读一个业务功能时应该沿哪条路径进入源码。完成后，能把前后端边界与后端模块职责说清楚，而不是从文件名开始漫无目的地浏览。

## 源码入口

- [RuoYi-Vue 项目仓库](https://gitee.com/y_project/RuoYi-Vue)
- [根目录 Maven POM](https://gitee.com/y_project/RuoYi-Vue/blob/master/pom.xml)：查看聚合工程和模块清单。
- [ruoyi-admin 的 RuoYiApplication.java](https://gitee.com/y_project/RuoYi-Vue/blob/master/ruoyi-admin/src/main/java/com/ruoyi/RuoYiApplication.java)：查看 Web 服务启动入口。
- [ruoyi-admin 模块 POM](https://gitee.com/y_project/RuoYi-Vue/blob/master/ruoyi-admin/pom.xml)：查看可运行应用装配了哪些模块。

RuoYi-Vue 是前后端分离的后台管理系统。阅读时可以把 Vue 管理端的页面与 API 调用视为客户端，把 Java 后端的 Controller、Service 和 Mapper 视为服务端主链路。具体仓库是否同时包含前端源码，要以所用发行包和分支为准。

## 调用链或模块关系

从一次页面请求入手，先沿“前端 API 调用 → `ruoyi-admin` 中的 Controller → 业务 Service → Mapper 与 SQL”向下追踪；再回到 `ruoyi-framework` 看安全、数据源和 Web 等基础配置，以及 `ruoyi-common` 提供的通用能力。

根 POM 将后端拆成多个 Maven 模块：`ruoyi-admin` 是 Web 应用入口，`ruoyi-framework` 承载框架配置，`ruoyi-system` 放置系统业务，`ruoyi-quartz` 处理定时任务，`ruoyi-generator` 提供代码生成，`ruoyi-common` 汇集公共代码。请求路径不一定穿过每个模块；从当前功能实际调用的类和依赖关系确认即可。

## 核心实现

`ruoyi-admin` 的启动类位于 `com.ruoyi` 包下。常见系统功能由 Controller 接收请求，再调用 `ruoyi-system` 中的业务接口和实现，最后通过 Mapper 访问数据。登录鉴权、异常处理、数据范围等横切行为通常要结合 `ruoyi-framework` 与 `ruoyi-common` 一起读，不能只看 Controller 的单个方法。

## 我的理解

我把项目拆成两张图来读：Maven 依赖图回答“代码放在哪个模块”，一次请求调用图回答“运行时经过哪些类”。模块名可以帮助缩小范围，但真实的职责边界要由 POM 依赖和实际调用共同验证。

## 可验证实验

1. 打开根目录 `pom.xml`，手动列出 `<modules>` 中的模块。
2. 查看 `ruoyi-admin/pom.xml`，确认 Web 应用依赖的模块；再沿一个 Controller 的注入接口找到 Service 和 Mapper。
3. 在 IDE 中对一个列表查询设置断点，从 Controller 单步进入 Service，记录 Mapper 方法和对应 SQL 文件。

以上目录与调用路径以当前阅读版本为参照；不同 RuoYi 版本、分支或二次开发仓库的具体路径和实现可能不同，请以本地 checkout 为准。
