# 目录与模块

## 本篇目标

用根 POM 和各模块的源码目录还原后端的职责边界，并分清“模块依赖”和“请求调用”是两种不同关系。读完后，可以判断一个新功能更可能落在哪个模块，以及下一步应该打开哪些文件。

## 源码入口

- [根目录 Maven POM](https://gitee.com/y_project/RuoYi-Vue/blob/master/pom.xml)：模块清单与统一依赖版本。
- [ruoyi-admin 目录](https://gitee.com/y_project/RuoYi-Vue/tree/master/ruoyi-admin)：Spring Boot 应用、Web 控制器和运行配置。
- [ruoyi-framework POM](https://gitee.com/y_project/RuoYi-Vue/blob/master/ruoyi-framework/pom.xml)：框架层依赖及基础设施。
- [RuoYi-Vue 仓库](https://gitee.com/y_project/RuoYi-Vue)：从当前分支确认实际目录。

## 调用链或模块关系

先从根 POM 的 `<modules>` 读取模块，再打开每个模块的 POM 核对依赖。主干关系可概括为：

```text
ruoyi-admin（Web 应用入口）
├── ruoyi-framework（Web、安全与基础设施）
│   └── ruoyi-system（系统业务）
│       └── ruoyi-common（公共代码）
├── ruoyi-quartz（定时任务）
│   └── ruoyi-common（公共代码）
└── ruoyi-generator（代码生成）
    └── ruoyi-common（公共代码）
```

这张图只表达代码组织和主要依赖方向，不表示每个 HTTP 请求都经过所有模块。常见源码目录是 `ruoyi-admin/.../web/controller`、`ruoyi-framework/.../framework`、`ruoyi-system/.../system` 与 `ruoyi-common/.../common`；`ruoyi-quartz` 和 `ruoyi-generator` 则按各自功能组织任务、模板及数据访问代码。

## 核心实现

Maven 聚合 POM 负责声明模块并统一版本；`ruoyi-admin` 负责把框架、业务与可选功能装配成可运行的 Web 应用。`ruoyi-system` 常见的业务切片是 domain、mapper、service：数据对象描述业务结构，Mapper 对接持久层，Service 承担业务操作。框架配置和公共注解、工具类会被多个业务切片复用。

阅读一个功能时，可以先由 URL 和 Controller 定位入口，再沿依赖注入追到 Service、Mapper 及 SQL；只有遇到鉴权、事务、数据范围或异常转换时，再回头读相关框架配置和切面。

## 我的理解

模块是编译和复用边界，不是业务流程图。理解目录的最好方式，是先从 POM 建立静态依赖图，再用一条真实请求验证哪些边界确实参与运行。

## 可验证实验

1. 在根 POM 中逐项勾出模块，并在各模块 POM 中记录 `ruoyi-*` 依赖。
2. 对照 `ruoyi-system` 的一个功能，分别找到其 Controller、Service 接口与实现、Mapper，以及 XML SQL（若该功能使用 XML）。
3. 在 IDE 的依赖视图中检查 `ruoyi-admin` 的传递依赖，比较它与根 POM 聚合模块列表的区别。

以上目录与调用路径以当前阅读版本为参照；不同 RuoYi 版本、分支或二次开发仓库的具体路径和实现可能不同，请以本地 checkout 为准。
