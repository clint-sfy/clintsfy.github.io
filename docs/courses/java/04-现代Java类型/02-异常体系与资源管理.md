# 异常体系与资源管理

## 学习目标

- 区分 `Error`、受检异常和 `RuntimeException`，划分可恢复错误边界。
- 使用 `throw`、`throws`、捕获顺序和异常翻译保留上下文与根因。
- 用 try-with-resources 自动关闭资源，并理解 suppressed exception 的来源。

## 核心知识点

### 专业术语

- **`Throwable` 层次**：`Error` 通常代表运行时环境严重故障，`Exception` 表示应用可以处理或传播的异常情况。
- **checked exception**：`Throwable` 中排除 `RuntimeException` 分支和 `Error` 分支后的异常；编译器要求调用方捕获或声明它们。
- **unchecked exception**：`RuntimeException` 及其子类与 `Error` 及其子类；前者常表示输入或状态错误，后者通常表示环境级严重故障。
- **异常链（exception cause）**：用 `new DomainException(message, cause)` 保留低层根因和高层语境。
- **try-with-resources**：自动调用 `AutoCloseable.close()` 的资源管理语句；关闭异常可记录为 suppressed exception。

### 白话解释与边界

异常不是万能返回值：可恢复的输入错误可以翻译成明确结果，编程错误应尽快暴露，`Error` 通常不应被业务代码吞掉。`throw` 抛出一个异常对象，`throws` 声明方法可能传播的异常（可以是 checked 或 unchecked，并不只描述 checked exception）；只有 checked exception 会触发编译器的捕获或声明检查。捕获顺序必须从具体到一般，否则子类分支永远不可达。重新抛出时保留 cause，日志还应带请求或文件上下文。

try-with-resources 按声明的逆序关闭资源，即使主体抛异常也会执行关闭；主体异常通常是主异常，关闭异常被放入 `getSuppressed()`。`finally` 中的 `return` 会覆盖原返回值或异常，资源清理应避免改变控制流。

## 简单案例

```java
import java.io.IOException;

public class ExceptionDemo {
    static final class TraceResource implements AutoCloseable {
        private final String name;

        TraceResource(String name) {
            this.name = name;
        }

        void read() throws IOException {
            throw new IOException("read failed");
        }

        @Override
        public void close() throws IOException {
            throw new IOException(name + " close failed");
        }
    }

    static int parsePort(String text) throws IOException {
        try {
            int port = Integer.parseInt(text);
            if (port < 1 || port > 65535) {
                throw new IllegalArgumentException("port range");
            }
            return port;
        } catch (NumberFormatException error) {
            throw new IOException("invalid port: " + text, error);
        }
    }

    public static void main(String[] args) {
        try (TraceResource resource = new TraceResource("file")) {
            resource.read();
        } catch (IOException error) {
            System.out.println("main=" + error.getMessage());
            System.out.println("suppressed=" + error.getSuppressed().length);
        }
        try {
            parsePort("abc");
        } catch (IOException error) {
            System.out.println("translated=" + error.getMessage());
        }
    }
}
```

输出会包含 `main=read failed`、`suppressed=1` 和 `translated=invalid port: abc`。资源关闭失败没有被吞掉，而是作为 suppressed 异常保存在主体异常中；低层的数字格式错误被翻译成带输入上下文的受检异常，并保留 cause。

## 易混点

- `RuntimeException` 不需要在签名中声明，但不代表它一定可以忽略；`Error` 更不应被通用 catch 当作业务失败处理。
- `throw` 是实际抛出，`throws` 是方法契约声明；只写声明不会自动处理异常。
- 捕获顺序必须先具体后一般，`catch (Exception)` 放在子类之前会导致编译错误。
- try-with-resources 的关闭异常通常是 suppressed，不是简单覆盖主体异常；不要用 finally 的 return 抹掉它。

## 课后小问

1. 为什么案例中 `getSuppressed().length` 是 1？
答案：主体 `read()` 先抛出异常，随后 `close()` 又失败，关闭异常被添加到主体异常的 suppressed 列表。
解析：try-with-resources 需要同时保留两个故障，调用方先处理主异常，再通过 suppressed 信息诊断资源关闭问题。

2. 异常翻译时为什么要传入原异常作为 cause？
答案：cause 保留低层失败的类型、消息和堆栈，调用者同时获得当前层的业务语境。
解析：只创建新异常会丢失根因，日志难以定位；`new IOException("invalid port", error)` 能形成可追溯的异常链。

## 本节小结

- `Throwable` 层次和 checked/unchecked 区分帮助划分恢复责任，不应盲目捕获所有异常。
- `throw` 抛出、`throws` 声明，异常翻译应保留 cause 与业务上下文。
- try-with-resources 自动按逆序关闭资源，关闭失败通过 suppressed exception 保留。
- finally 只做清理，不要用 return 覆盖原异常或结果。

## 快速回顾

- 能判断一个异常应在当前层恢复、翻译还是继续传播。
- 能写出具体到一般的 catch 顺序。
- 能解释 try-with-resources 的关闭顺序和 suppressed 语义。
- 能在自定义异常中保留 cause、输入和资源上下文。
