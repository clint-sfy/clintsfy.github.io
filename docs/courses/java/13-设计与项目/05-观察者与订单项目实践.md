# 观察者模式与订单项目实践

观察者模式让事件发布者通知多个订阅者，适合一个业务动作需要触发多个独立处理的场景。先理解同步调用，再决定是否需要消息队列。

## 同步通知如何工作

发布者保存监听器，事件发生后逐个调用。上面的两个监听器在 `publish` 返回前依次执行，因此输出先是通知再是审计。监听器执行缓慢会延长发布者等待时间；如果第一个监听器抛异常，当前实现不会调用第二个。需要隔离失败时，应明确记录失败并制定重试策略。

订阅关系减少了发布者对具体处理方式的了解，但增加了排查路径：阅读创建订单的方法时，后续处理可能分布在多个监听器中。只有确实存在多个独立响应者时才引入事件；一个固定步骤直接调用通常更容易理解。

## 事件协作

### 观察者模式：发布事件并通知订阅者

下面是普通 Java 内存示例，可以整体粘贴到 JDK 17+ 的 JShell；`publish` 按注册顺序同步调用监听器。

```java
import java.util.ArrayList;
import java.util.List;
import java.util.function.Consumer;
record OrderCreated(String orderId) {}
class EventBus {
    private final List<Consumer<OrderCreated>> listeners = new ArrayList<>();
    void subscribe(Consumer<OrderCreated> listener) { listeners.add(listener); }
    void publish(OrderCreated event) {
        for (var listener : listeners) listener.accept(event);
    }
}
var bus = new EventBus();
bus.subscribe(event -> System.out.println("通知: " + event.orderId()));
bus.subscribe(event -> System.out.println("审计: " + event.orderId()));
bus.publish(new OrderCreated("O-1"));
// 输出：通知: O-1，然后审计: O-1
```

这是同步、单线程教学实现：监听器抛异常会中断后续通知，进程退出后事件也不会保留。它没有线程安全、重试或持久化保证，不能直接当作可靠消息系统。

### 事务与事件：明确成功边界

假设订单写库后要发消息：在数据库事务提交前发送，后续回滚可能产生不存在订单的通知；提交后直接发送，进程崩溃又可能漏发。可靠投递通常把订单和待发送事件写入同一数据库事务，再由独立任务发送并标记状态（事务性 outbox）。

消费者仍可能收到重复消息，应以稳定事件 ID 做幂等处理；失败重试、消息顺序和死信处理都要按业务约定。单纯的内存监听器不能提供这些保证。

## 订单服务的边界

### 订阅与取消：管理监听器生命周期

长生命周期的发布者持有监听器引用；如果订阅者不再需要通知，应允许取消订阅，否则对象可能一直无法回收。下面是可独立粘贴到 JShell 新会话的完整例子：

```java
import java.util.ArrayList;
import java.util.List;
import java.util.function.Consumer;
record OrderCreated(String orderId) {}
class EventBus {
    private final List<Consumer<OrderCreated>> listeners = new ArrayList<>();
    void subscribe(Consumer<OrderCreated> listener) { listeners.add(listener); }
    void unsubscribe(Consumer<OrderCreated> listener) { listeners.remove(listener); }
    void publish(OrderCreated event) {
        for (var listener : listeners) listener.accept(event);
    }
}
var bus = new EventBus();
Consumer<OrderCreated> listener = event -> System.out.println(event.orderId());
bus.subscribe(listener);
bus.publish(new OrderCreated("O-1")); // 输出：O-1
bus.unsubscribe(listener);
bus.publish(new OrderCreated("O-2")); // 无输出
```

调用者保存最初传给 `subscribe` 的同一个监听器引用，再传给 `unsubscribe`。不能指望重新写一个相同内容的 lambda 一定等于原对象。示例使用 `ArrayList`，通知期间修改订阅列表可能触发并发修改异常；多线程环境需要明确同步和通知时的快照策略。

### 事件内容：传递稳定事实

`OrderCreated` 描述已经发生的事实，订单 ID 让监听器知道要处理哪个订单。实际系统可加入事件 ID、发生时间和必要的业务快照；如果监听器稍后查询订单，读到的状态可能已经变化，不能假设它还是事件发生时的状态。

事件中避免放密码、令牌等敏感数据，并为字段演进制定兼容规则。事件 ID 用于识别重投，订单 ID 标识业务对象，两者用途不同：同一订单可能产生多个事件。

### 失败与重试：先决定处理策略

同步监听器失败时，上面的 `publish` 会直接抛异常并跳过后续监听器；若调用方捕获异常继续执行，需要记录哪个处理失败，不能默默吞掉。通知邮件可允许稍后重试，但库存扣减等核心状态不能简单依赖易丢失的内存回调。

使用 outbox 时，发送成功后、标记完成前崩溃可能再次发送，所以消费者应在同一事务中检查事件 ID 并执行本地状态变更。外部邮件或支付接口还需使用对方支持的幂等键，不能仅凭本地去重声称端到端恰好一次。

### 订单服务：先定义业务边界

从“创建订单”开始，约定输入包含商品、数量和请求唯一键；成功返回订单编号，非法数量或库存不足返回明确错误。金额使用整数分或明确舍入规则的 `BigDecimal`，不要用 `double` 直接计算货币。

先写内存版本并覆盖正常创建、数量为零、库存不足和重复请求；再抽出库存与订单存储接口。接口是为了隔离确实不同的职责，不必提前为每个类增加一层。

### 事务：原子保存状态

接入数据库后，在一个事务内完成扣库存、保存订单和写 outbox。扣库存需由数据库条件更新等并发控制保障，例如更新条件包含 `stock >= quantity`，并检查受影响行数；单靠先查询再更新会有并发竞态。失败时回滚整个事务。

### 测试：覆盖业务与集成边界

单元测试可用内存实现验证价格与状态转换；数据库集成测试验证事务回滚、并发扣减和唯一约束。针对重复请求和重复事件分别验证幂等，不要只检查成功路径。

## 易混点

观察者描述发布者和订阅者之间的协作，不自动提供异步、持久化或可靠投递。异步执行可以缩短请求等待，却引入任务丢失、异常处理和关闭时等待等新问题；消息队列也不能省略消费者幂等。
