# 高可用与性能

## 先规划故障域

KRaft controller quorum 管元数据，Broker 存储并提供消息读写；生产环境应根据故障域规划 controller、Broker、分区副本和容量。图片中的 ZooKeeper 集群内容可用于理解历史架构，但新集群按 KRaft 建设。[KRaft 文档](https://kafka.apache.org/documentation/#kraft)。

## 分区数不是越多越好

分区提高消费组内并行度，同时增加元数据、文件句柄、复制和再均衡成本。先用目标吞吐、单分区测试结果、消费实例数量与故障恢复时间估算，再做压测；增加分区还可能影响 key 的后续路由。

## Producer 批量和压缩

`batch.size`、`linger.ms`、压缩类型会影响吞吐、延迟与 CPU。先明确端到端延迟预算，再比较不同配置；只看发送 API 返回速度会遗漏 Broker 持久化和消费积压。零拷贝减少某些数据传输路径的内核/用户态复制，但不能替代分区规划或容量监控。

## 生产观察项

持续看生产请求延迟与错误、ISR 缩减、欠复制分区、磁盘余量、消费 lag、再均衡频率和请求队列。重启与滚动升级先核对版本兼容矩阵及控制面状态。[Kafka 运维文档](https://kafka.apache.org/documentation/#operations)。
