# 高可用、性能与总结选型

## 先规划故障域

KRaft controller quorum 管理元数据（Topic 列表、分区 Leader 分配等），Broker 存储并提供消息读写。生产环境应根据故障域规划 controller、Broker、分区副本和容量。

什么是"故障域"？简单说就是：一台机器挂了，影响范围有多大。把 controller 放在不同物理机上，一台挂了还有其他 controller 投票选出新 Leader；把分区副本分布到不同机架甚至不同机房，一个机架断电后其他副本仍可服务。

KRaft 是 Kafka 自带的元数据管理机制，Kafka 4.0 已完全移除 ZooKeeper 模式。旧文档中的 ZooKeeper 集群内容只适合维护历史集群，新集群统一按 KRaft 建设。[KRaft 文档](https://kafka.apache.org/documentation/#kraft)。

Controller 负责元数据决策，不是每条业务消息都先经过 Controller。数据仍由分区 Leader 所在 Broker 直接处理，所以 Broker 故障和 Controller 故障是两个不同的故障层面。故障时先看控制面是否能选出有效 Leader，再看业务分区是否有足够 ISR 接受写入。Controller 多数派和业务副本 ISR 是两种不同的可用性条件。

## 分区数不是越多越好

分区提高消费组内并行度——一个消费组里每个实例最多处理一个分区，所以分区数就是同组并行处理的上限。但分区越多，元数据、文件句柄、复制开销和再均衡时间都会增加。

举个例子：一个 Topic 有 3 个分区、同一消费组有 2 个实例。常见分配是一个实例负责 2 个分区、另一个负责 1 个。如果你想扩到 4 个实例同时工作，分区数至少要是 4，否则多出的实例会空闲。

那为什么不一上来设 100 个分区？因为：

- **元数据膨胀**：每个分区在 Broker 上都有对应的日志目录和索引文件，100 个分区 × 10 个 Topic 就是 1000 个目录。
- **再均衡变慢**：消费者加入或退出时，协调器要重新分配所有分区，分区越多越慢。
- **复制开销**：每个分区都有副本，副本间的数据同步也需要网络和磁盘资源。

正确做法是先用目标吞吐量、单分区测试结果、消费实例数量与故障恢复时间做估算，再压测验证。注意：增加分区数还可能改变后续消息的 key 路由，因为 `hash(key) % partitionCount` 的结果会变。

### 分区与顺序的关系

如果一个订单必须严格按顺序处理（比如先创建、再支付、再发货），把订单 ID 作为消息 key，Kafka 会把相同 key 的消息路由到同一分区，保证该订单的事件按写入顺序排列。但不同订单之间没有全局顺序——订单 A 的消息可能在分区 0，订单 B 的消息可能在分区 1，两者并行处理互不干扰。

## Producer 批量和压缩

Kafka Producer 不会每条消息立即发送到 Broker，而是先攒成一批。三个关键参数控制批量行为：

| 参数 | 作用 | 影响 |
| --- | --- | --- |
| `batch.size` | 单分区批次的最大字节大小 | 太小则批次频繁发送，网络效率低 |
| `linger.ms` | 等待凑批的最大毫秒数 | 设为 5 表示最多等 5 毫秒凑批 |
| `compression.type` | 批次压缩方式（none/gzip/snappy/lz4/zstd） | 压缩减少网络字节量，但消耗 CPU |

举个例子：`linger.ms=5` 意味着 Producer 收到一条消息后不会立即发送，而是最多等 5 毫秒看有没有更多消息一起发。如果 5 毫秒内又来了 10 条，它们会放在同一个批次里一次性发送，减少网络请求次数。对延迟敏感的场景设 0（立即发送），对吞吐敏感的场景设 10~50。

零拷贝（sendfile）是操作系统级别的优化：Broker 把磁盘上的日志数据直接通过网卡发送，不需要数据从内核空间复制到用户空间再复制回内核。这减少了 CPU 消耗和内存拷贝，但不能替代分区规划或容量监控——如果你的分区数设计不合理，零拷贝也救不了。

## 生产观察项

上线后需要持续关注以下指标：

| 指标 | 含义 | 异常含义 |
| --- | --- | --- |
| 生产请求延迟与错误率 | Producer 发送到 Broker 的耗时和失败比例 | 延迟上升可能是 Broker 负载高或网络问题 |
| ISR 缩减 | 同步副本数减少 | 副本跟不上 Leader，可能磁盘慢或网络拥塞 |
| 欠复制分区（URP） | 副本数低于设定值的分区 | 部分副本不可用，数据有丢失风险 |
| 磁盘余量 | Broker 磁盘剩余空间 | 消息保留策略不当会导致磁盘写满 |
| 消费 lag | 消费者落后于最新消息的数量 | 消费速度跟不上生产速度，消息积压 |
| 再均衡频率 | 消费组成员变更次数 | 频繁再均衡说明实例不稳定或心跳配置不当 |

重启与滚动升级前先核对版本兼容矩阵及控制面状态。[Kafka 运维文档](https://kafka.apache.org/documentation/#operations)。

## 一条消息的完整路径回顾

学到这里，可以把整个 Kafka 链路串起来看：

```
业务产生事件
  → Producer 按 key 选择分区并等待确认（acks=all 时等 ISR 副本）
    → Broker Leader 追加日志并复制到 Follower
      → ISR 满足后向 Producer 返回 ACK
        → Consumer Group 分配分区给组内实例
          → Consumer 拉取消息、处理业务、提交 offset
```

这条链路上任一箭头都可能失败，**不能用"消息发出去了"概括全链路**：

- Producer 发送后没收到 ACK：消息可能已写入 Broker，也可能没有（不确定状态）。
- Broker 确认后、Consumer 读到前：消息安全存储，但还没产生业务价值。
- Consumer 读到后、提交 offset 前：处理成功了但重启可能重读。
- Consumer 提交 offset 后、业务效果生效前：消息被标记为已处理但业务可能没完成。

每一步的失败都需要对应的处理策略：Producer 重试和幂等、Broker 副本和 ISR、Consumer 幂等和死信队列。

## 什么时候适合 Kafka

| 场景 | 是否适合 Kafka | 原因 |
| --- | --- | --- |
| 多个下游独立读取同一事件 | 适合 | 不同消费组各自保留进度，互不影响 |
| 高吞吐事件流（日志、监控、用户行为） | 适合 | 顺序磁盘写入 + 零拷贝，单机每秒百万级消息 |
| 需要保留并重放历史事件 | 适合 | 消息不会因消费而删除，可按 offset 重读 |
| 按分区严格顺序处理 | 适合 | 同 key 消息进同分区，分区内有序 |
| 只需要一个服务同步获得结果 | 不适合 | 直接 HTTP 调用更简单，加 MQ 反而增加复杂度 |
| 任务量很小且没有运维团队 | 不适合 | 集群和消费运维成本超过收益 |
| 需要严格的事务消息（像数据库事务） | 部分支持 | Kafka 事务仅覆盖 Kafka 内部读写，不能自动保证外部系统 |

选型时问自己三个问题：**我的场景需要重放吗？需要多组独立读取吗？吞吐量足够大到值得运维一个集群吗？** 如果三个都是"否"，先选简单方案。

## 与其他消息队列的对比速查

| 特性 | Kafka | RabbitMQ | RocketMQ | ActiveMQ |
| --- | --- | --- | --- | --- |
| 消息保留 | 按保留期持久存储 | 消费后删除 | 支持持久存储 | 消费后删除 |
| 多消费组独立读 | 支持，各自 offset | 不支持，一条消息只投递一次 | 支持 | 不支持 |
| 吞吐量 | 极高（百万/秒） | 中等（万级/秒） | 高（十万级/秒） | 中低 |
| 顺序保证 | 分区内有序 | 队列内有序 | 分区内有序 | 队列内有序 |
| 事务消息 | Kafka 事务（内部） | 不支持 | 支持事务消息 | 支持 JMS 事务 |
| 适用场景 | 事件流、日志、监控 | 任务队列、RPC 路由 | 电商事务消息 | 传统企业消息 |

不要只比较"能不能发消息"，要看是否需要重放、多组独立读取、顺序范围、吞吐与运维能力。

## 下一步

掌握这些后，再结合真实项目做一个"订单创建 → 事件 → 投影服务"的小闭环，并验证以下四种情况：

1. **重复投递**：手动发两条相同 key 的消息，观察消费者是否做了幂等。
2. **消费者重启**：杀掉消费者进程再重启，确认它从上次提交的 offset 继续。
3. **Broker 故障**：停掉 Broker 再启动，观察 Producer 重试和 Consumer 自动重连。
4. **消息积压**：临时让消费者 sleep 模拟处理慢，观察 lag 增长和恢复。

做完这四个实验，才算真正理解了 Kafka 的可靠性和故障边界。
