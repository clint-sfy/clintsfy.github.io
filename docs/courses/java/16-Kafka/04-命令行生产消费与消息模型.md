# 命令行生产消费与消息模型

## 一条消息走过哪里

在 Kafka 中，一条消息从产生到被消费，经过的路径是：

```
Producer（生产者）
  → 选择 Topic 和分区
    → 把记录追加到该分区的日志末尾
      → Consumer（消费者）按分区 offset 读取
```

**Topic** 是消息的逻辑分类名，比如 `order.events`（订单事件）或 `user.activity`（用户行为）。一个 Topic 可以分成多个**分区（partition）**，每个分区是一个有序的、不可变的追加日志。消息写入分区后获得一个递增的**offset**（位移号），从 0 开始。

Producer 发送消息时可以指定 key。**相同 key 的消息通常进入相同分区**，因为分区选择算法是 `hash(key) % partitionCount`。这样做的好处是：同一订单的所有事件（创建、支付、发货）会按写入顺序排列在同一分区内，保证顺序处理。但注意：**增加分区数可能改变之后消息的映射**，因为 `hash(key) % partitionCount` 的结果会变，不能把 key 当作永远稳定的分区号。

## 命令行收发：两个终端完成一轮

先按[快速入门](./03-Kafka快速入门与安装)创建 `learning.events` Topic。然后打开两个 PowerShell 终端，一个做消费者，一个做生产者。

### 步骤一：终端 A 启动消费者

```powershell
docker exec -it kafka-lab /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic learning.events --from-beginning
```

这个命令的含义拆解：

| 参数 | 含义 |
| --- | --- |
| `docker exec -it kafka-lab` | 进入名为 kafka-lab 的容器，分配交互终端 |
| `--bootstrap-server localhost:9092` | 连接 Kafka Broker 的地址 |
| `--topic learning.events` | 订阅哪个 Topic |
| `--from-beginning` | 从分区最早可用消息开始读 |

启动后终端会"卡住"等待消息，这是正常行为——消费者在持续轮询。

### 步骤二：终端 B 启动生产者

```powershell
docker exec -it kafka-lab /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic learning.events
```

出现 `>` 提示符后输入 `hello` 并回车，终端 A 会立即显示 `hello`。

### 步骤三：多发几条试试

在终端 B 继续输入：

```
> hello
> world
> order-7 created
```

每输入一行就是一条新消息，终端 A 会逐行显示。两边都可以按 `Ctrl+C` 结束。

### `--from-beginning` 的含义

如果你重启终端 A 但不加 `--from-beginning`，可能看不到之前发的消息。这是因为不加此参数时，消费者会使用消费组的已提交 offset 作为起点；新消费组没有 offset 时默认从最新位置开始读（`latest` 策略），所以只能收到之后新发的消息。

`--from-beginning` 强制从保留期内的最早消息开始读，适合练习时查看历史消息。生产环境一般不用这个参数，而是依赖消费组自身的 offset。

## 消息的组成部分

上面的命令行例子默认只打印 value，所以你看不到 key、分区和 offset。实际上一条 Kafka 消息包含多个部分：

| 部分 | 说明 | 示例 |
| --- | --- | --- |
| **Topic** | 消息属于哪个主题 | `learning.events` |
| **Partition** | 消息被写入哪个分区 | `0` |
| **Offset** | 消息在分区中的位置号 | `3` |
| **Key** | 用于分区路由的标识，可为 null | `order-7` |
| **Value** | 消息内容本身 | `created` |
| **Timestamp** | 消息时间戳 | `1730822400000` |
| **Headers** | 可选的元数据键值对 | `source=java-demo` |

下一章的 Java `ProducerRecord` 会把这些字段都明确写出来，你会看到完整的消息结构。

### 看到不等于处理成功

不要把"终端打印了 hello"误解成下游业务已处理成功。它只证明消费者**读到了**消息字节数据。消费者读出消息后，可能解析失败、数据库写入失败、或者进程在处理过程中崩溃。消息读取和业务成功是两个独立事件。

## 几个关键位置的概念

Kafka 中有多个"位置"概念，初学者很容易混淆。下面用快递站类比来理解：

### 写入 offset（包裹在货架上的位置号）

每条消息写入分区时获得一个递增编号。分区 0 的前三条消息的 offset 分别是 0、1、2。这个编号是 Broker 分配的，消费者不能修改。

### 当前消费位置（取到哪个包裹了）

消费者读取消息时，客户端内存中维护一个"下一位置"。读完 offset 0 后，下一位置是 1；读完 1 后，下一位置是 2。这是消费端的临时状态。

### 已提交 offset（取件记录本）

消费者把"已经处理到哪里"的位置提交给 Broker 保存，作为恢复点。如果消费者崩溃重启，会从已提交的 offset 继续。**已提交 offset 和当前消费位置不一定是同一个值**：你可能读到了 offset 5 但只提交到了 offset 3，重启后会从 offset 3 重新读。

### 具体例子

假设分区 0 有三条消息，offset 分别是 0、1、2：

1. 消费者处理完 offset 0 和 1，当前消费位置是 2（下一条要读 2）。
2. 此时调用 `commitSync()` 提交 offset 2。
3. 消费者崩溃前还没处理 offset 2，重启后从 offset 2 继续——不丢不重。
4. 如果处理完 offset 1 但**尚未提交**就崩溃，重启后从上次提交的 offset 0 之后开始——会重新处理 offset 1。

第 4 种情况就是"至少一次"语义下的重复来源：消息不会丢（因为没提交就不会跳过），但可能重读。所以业务侧需要用消息 ID 做幂等处理。

## 查看 Topic 详情

用下面的命令查看 Topic 的分区和副本信息：

```powershell
docker exec kafka-lab /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic learning.events
```

输出类似：

```
Topic: learning.events	PartitionCount: 1	ReplicationFactor: 1	Configs:
	Topic: learning.events	Partition: 0	Leader: 1	Replicas: 1	Isr: 1
```

| 字段 | 含义 |
| --- | --- |
| `PartitionCount` | 分区数，当前为 1 |
| `ReplicationFactor` | 副本数，当前为 1（单节点实验） |
| `Leader` | 当前分区的 Leader Broker 编号 |
| `Replicas` | 该分区的所有副本所在 Broker |
| `Isr` | 当前同步的副本集合（In-Sync Replicas） |

单节点实验中 Leader、Replicas 和 Isr 都是同一个 Broker，不能验证多副本容错。多副本的意义在[存储、复制与可靠性](./08-存储复制与可靠性)中详细讨论。

## 查看消费组状态

```powershell
docker exec kafka-lab /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --list
```

先列出所有消费组名，再查看具体组的 offset 状态：

```powershell
docker exec kafka-lab /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group learning-demo-xxx
```

输出会显示该消费组在每个分区上的 `CURRENT-OFFSET`、`LOG-END-OFFSET` 和 `LAG`。LAG 是消费组落后于最新的消息数——如果 LAG 持续增长，说明消费速度跟不上生产速度，需要排查消费者处理逻辑或增加实例。

[Kafka Consumer 文档](https://kafka.apache.org/documentation/#consumerapi)。
