# 命令行生产消费与消息模型

## 一条消息走过哪里

Producer 选择 Topic 和分区，把记录追加到该分区；Consumer 按分区 offset 读取。相同 key 通常落在同一分区，但增加分区数可能改变之后消息的映射，不能把 key 当作永远稳定的分区号。

## 命令行收发：两个终端完成一轮

先执行[快速入门](./03-Kafka快速入门与安装)创建 `learning.events`。打开两个 PowerShell 终端。终端 A 先启动消费者：

```powershell
docker exec -it kafka-lab /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic learning.events --from-beginning
```

终端 B 启动生产者，出现 `>` 后输入 `hello` 并回车：

```powershell
docker exec -it kafka-lab /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic learning.events
```

终端 A 会显示 `hello`。终端 B 每输入一行就是一条新消息；两边都可以按 `Ctrl+C` 结束。若终端 A 还显示之前的消息，是因为 `--from-beginning` 会从保留期内的最早位置开始读。

这个例子默认只看 value，所以看不到 key、分区和 offset；下一章 Java `ProducerRecord` 会把 key 明确写出来。不要把“终端打印了 hello”误解成下游业务已处理成功，它只证明消费者读到了消息。

## 一句话分清几个位置

写入 offset 表示消息在分区日志的位置；当前消费位置表示下一条要取哪里；已提交 offset 是消费组重启后的恢复点。它们不是同一个值。[Kafka Consumer 文档](https://kafka.apache.org/documentation/#consumerapi)。

假设分区 0 的三条消息 offset 分别是 0、1、2。消费者处理完 offset 1 后，下一位置是 2；若提交的是 2，重启会从 2 继续。若处理完 1 却尚未提交就崩溃，重启可能再次处理 1，这就是“至少一次”场景里的重复来源。
