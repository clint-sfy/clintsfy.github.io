# GC 日志与问题定位

## 学习目标

- 用统一 GC 日志识别 Young GC、Full GC、长停顿和 safepoint 问题。
- 区分分配过快、老年代晋升、缓存泄漏、大对象和堆过小。
- 建立“现象—证据—改动—结果”的可回滚调优闭环。

## 核心知识点

### 专业术语

- **分配速率（allocation rate）**：单位时间内新对象分配的字节量。
- **存活集（live set）**：一次回收后仍由根可达的对象集合。
- **晋升压力（promotion pressure）**：对象存活时间变长，进入老年代或长期区域的压力。
- **Safepoint**：所有 Java 线程到达可安全检查/暂停的位置。
- **GC 日志**：记录触发原因、区域变化、停顿、并发阶段和收集器决策的证据。

### 白话解释与边界

日志先回答“多久发生一次、停多久、回收前后剩多少、为什么触发”。频繁 Young GC 可能是分配速率高，Full GC 可能是老年代逼近上限、显式 GC、元空间压力或收集器策略；单看次数不能定性。

定位时保持基线：应用版本、JDK、收集器、Xms/Xmx、CPU/容器限制、请求量和代码版本都要记录。一次只改一个参数，并在同样负载下比较 p95/p99 停顿、吞吐、RSS、分配和存活量。

## 易混点

- Young GC 频繁不一定是泄漏，Full GC 多也不一定是泄漏；看回收后存活集和引用链。
- GC 停顿和 safepoint 停顿可能不是同一件事，要分别采集。
- 堆占用低但 RSS 高时，排查线程栈、元空间、直接内存和 native 库。
- G1 大对象、容器缓存和序列化缓冲可能产生 Humongous 压力，单纯调大堆不一定有效。
- 调参必须同版本、同负载、同指标比较，不能只凭一条日志或一次压测结论。

## 课后小问

1. Full GC 后老年代占用仍持续上升说明什么？
答案：更像长生命周期引用增长、缓存泄漏或队列积压，但仍需引用链确认。
解析：如果回收后存活量不高，优先检查堆大小、触发原因、显式 GC 和分配速率。

2. 为什么要把 GC 日志和业务 QPS 对齐？
答案：GC 频率、分配速率和停顿往往随负载变化，孤立日志无法判断是否由流量突增导致。
解析：按相同时间窗对齐请求量、错误率、延迟、分配和停顿，才能比较改动前后。

3. 什么时候需要堆转储而不是继续看日志？
答案：当需要知道哪些对象被谁引用、缓存为何不能回收时。
解析：日志能说明时间和容量趋势，堆转储和分析工具才能给出对象引用链；采集前要评估停顿和敏感数据。

## 本节小结

- GC 日志首先看触发原因、频率、停顿和回收后存活量。
- 分配过快、晋升压力、缓存泄漏、大对象和非堆内存会呈现不同证据。
- jstat/jcmd 适合快速采样，GC 日志/JFR/堆转储用于更深分析。
- 以基线和同负载回归为调优闭环，一次只改一个可回滚变量。

## 快速回顾

- 会用 `-Xlog:gc*` 和 safepoint 日志建立证据。
- 能区分 Young GC、Full GC、泄漏、分配过快和大对象压力。
- 会按需要选择 jstat、jcmd、直方图、堆转储或 JFR。
- 能写出“现象—证据—改动—结果”的问题定位记录。
